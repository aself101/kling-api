## [2.0.0] - 2026-09-20

### Fixed
- `TaskHandle.wait()`: a caller that re-joined a handle right after the previous caller aborted or timed out was rejected with the shared poll loop's own `AbortError` and never polled (abort-then-retry on one handle could not work). The loop's self-abort is no longer a subscriber failure and a fresh loop starts when subscribers remain.
- `KlingPollTimeoutError.task` from `wait()` now carries the last task polled (it was always `null`).
- `save()` refuses a `task.id` that is not a single path segment before it becomes a file name (a callback body parsed without a secret is untrusted input); a failure after earlier files were written now throws `KlingSaveError { written, failedUrl, cause }`; video downloads default to a 120 s deadline (they were on the 60 s image/audio one).
- Downloads: a caller abort during the body read is rethrown unwrapped (it surfaced as `KlingDownloadError('http')`); the hop deadline is `reason: 'timeout'`; a missing or malformed `Location` is `'invalid-redirect'`; the DNS lookup of the URL safety check now runs inside the hop deadline and honours the caller's abort.
- `HttpCore`: a caller abort during the retry backoff rejects immediately (it waited out the sleep, up to 30 s); `KlingResponseError` carries the `JSON.parse` error as `cause`.
- URL safety: hex-embedded IPv4 forms (`::7f00:1`, `64:ff9b::7f00:1`) are refused like their dotted spellings.
- CLI: the paid task id is printed (stdout, `--json`-aware) even when `--wait` or the save fails; errors set `process.exitCode` instead of calling `process.exit()` on the same tick (a large `--json` error body was truncated at the 64 KiB pipe buffer); `tasks list --days 0` is a zero-width window, not "unset"; every commander option bag crosses one typed boundary (`handler<T>()`).
- Dead 1.x `utils/{index,file-io,logger}` modules and unused constants are gone from the tarball; stale phase-anchored preambles that shipped in `dist/*.d.ts` are rewritten.
### Changed
- **An unknown value from the vendor no longer fails a whole page.** `parseStatus` still refuses to guess — a status neither standard defines throws, because `wait()` polling an unrecognised status forever is worse than an error — but list reads now isolate per record: the bad one is dropped and returned in `malformed[]` (`{ path, reason, raw }`) while the rest of the page comes back. `tasks.get`, `tasks.list`, `listByProduct` and the resource list/presets methods all carry it, and the CLI prints it beneath the table. Single-task reads (`getByProduct`, `recover`) still throw, and a page where *nothing* parsed still throws — that is the wrong codec, not one unknown value. The vendor has already changed a status spelling once (`succeed` → `succeeded`); the previous behaviour turned that class of change into a total read outage on tasks the caller had already paid for. `malformed` is returned rather than only logged because the default logger is `silentLogger`.

### Fixed
- **Documentation caught up with the behaviour changes in this release.** Seven README passages still described superseded behaviour: "Polling at scale" said `wait()` does not batch across handles (it does, since this release); the downloads note called `maxBytes` a per-call heap ceiling 23 lines after the same section said `save()` streams; the retry policy described a deterministic backoff with no mention that `retry.jitter` now defaults to `'equal'`; `KlingAPIError.retryAfterMs` appeared nowhere; the `KlingBatchError` row did not say a caller abort is rethrown unwrapped rather than wrapped; `healthCheck()` was documented as `false` on any throw, without the abort exception; and a read-after-write caveat still said "unmeasured" while Known limits carried the measurement. `fetchToFile` and `HttpCoreInternals` are now in the advanced-exports table. `test/2.0/packaging.test.ts` anchors four of these claims to the source that decides them.
- **`@types/node` is a real dependency, not a dev one.** The published `.d.ts` files name the Node global `Buffer` (`codecs/params`, `media/download`, `media/source`), so a TypeScript consumer installing the tarball got four errors from inside our own types and could not compile against the package at all. Every in-repo check was blind to it — build, tests and lint are green here because `@types/node` is always present locally. Caught by installing the real tarball from a local registry into a scratch consumer, which is the entire point of publishing to Verdaccio before npm. `test/2.0/packaging.test.ts` now fails if emitted types name a Node global without the types package being declared.

### Changed

**Verified against the live vendor API before release** (2026-09-22; probe scripts in `scripts/`):
- **Read-after-write lag: measured, none found.** 19 live tasks read back at t ≈ 0 / 100 ms / 500 ms / 2 s on both `task_ids` and `external_task_ids` — 152 reads, 0 misses. The unattended protocol rested on "~4 tasks showed no lag"; a `KlingTaskNotFoundError` on a first poll is now an anomaly rather than an expected race. Also confirmed the hard way: killing the client does not cancel the task — seven tasks from a run killed at a timeout completed and billed in full.
- **The duplicate `external_task_id` check holds in every scope that the double-bill guidance depends on**, and one it did not assume: refused `1201 / not-created` immediately and ~13 minutes later, on a new-standard create and a legacy one, and **across products** — the id namespace is account-wide, so a cross-product retry cannot double-bill either. The prior evidence was a single same-product, immediate, after-success observation. Unobserved still: a re-submit after a *failed* original.
- **A refused create costs nothing** — seven `1303` refusals left the balance unchanged to the unit, confirmed against `packageLedger`. The README carried this as an open question.
- **Units are deducted on completion, not submission**, so a balance read right after a create still shows the old number.
- **The concurrency ceiling is in the pack name** (`Trial-Video-100Units-5Con-1Months`) and counts tasks *in flight*, not creates in flight: a task holds its slot for the ~30-60 s it renders after the create returns. Freeing the slot on the create response took `1303` on 7 of 10 creates.
- **`outputsExpireAt` is right to the second on video too** — compared against the vendor's signed-URL `Expires=` on five new-standard video tasks, the derived value landed 1.1-2.1 s *after* the vendor's every time (the one prior comparison was a legacy image). It errs late, by ~2 s at the end of 30 days.
- **Batched polling and streamed `save()` confirmed against the real API**: five concurrent `wait()` handles issued 3 `GET /tasks` over 3 ticks instead of 15 (80% fewer, one request carrying all five ids), and `save()` pulled a real CDN body to disk. No codec warnings on any live response — every field the vendor returned is modelled.

- The DNS-rebinding limitation on the SSRF guard (CWE-367) is now documented **with a tested mitigation** rather than only acknowledged: the README carries a pinned-`fetch` recipe, and `test/2.0/media/pinning.test.ts` exercises it against a local TLS server with a control proving the pin decides the destination. The library still does not pin by default — that needs a 2 MB fourth runtime dependency to close a hole whose exploitation requires control of the vendor's own CDN DNS.
- **`save()` streams to disk instead of buffering the whole output.** `maxBytes` (500 MiB for video) was a per-call heap ceiling presented as a protective byte cap — saving several videos concurrently could exhaust memory. Each output now streams straight into the temp file it was already going to be renamed from, so the cap bounds the file and not the heap. Measured on a 220 MB body: **+52 MB streamed, +389 MB buffered.** New public `fetchToFile(url, path, options)` carries the same byte, redirect and per-hop SSRF guards as `fetchToBuffer`, which is unchanged for callers that want the bytes. A failure at any point removes the partial file, so no truncated output is ever left at the destination.
- **Polling no longer scales linearly in requests.** `TaskHandle.wait()` polled one id per handle, so N in-flight tasks were N `GET /tasks` per tick against an API that answers `1303 "parallel task over resource pack limit"`. Single-id reads from one client that land in the same turn are now merged into the vendor's 20-id batch, and the poll cadence is quantised to a shared grid so handles created at different moments converge onto the same turn. Measured over 25 handles to terminal: **6-8 requests, from 52-70.** The batch window is one `setTimeout(…, 0)` — a microtask flush fires while other handles are still mid-`await` and batches nothing (77 requests). Per-caller semantics are unchanged; the one trade is that a caller's `signal` no longer aborts the underlying request, because it is shared — it still rejects that caller immediately, exactly as the shared poll loop has always worked across subscribers on one handle.
- **Retry backoff is jittered and honours `Retry-After`.** `retry.jitter` (`'equal'` default, `'none'` for a reproducible schedule) waits `delay/2 + random(0, delay/2)`, so clients that failed on the same burst do not retry in lockstep — the deterministic `baseDelayMs * 2^n` schedule was itself a thundering-herd generator. When the vendor sends `Retry-After` (delta-seconds or HTTP-date) it wins over our own backoff, capped by `maxDelayMs`, and is exposed as `KlingAPIError.retryAfterMs` so a consumer re-submitting a create can honour it too. Note the poll interval is deliberately **not** jittered: aligned polls are what the batching feeds on.
- Documentation gaps from the ship review closed: the retry note states **both** read-retry spans (~6 s on a fast refusal, ~96 s on timeouts — the backoff is the same, the attempt is not) instead of leading with the optimistic one; the CLI reference carries the flags it had omitted (`--negative-prompt`, `--image-reference`, `--image-fidelity`, `--element`, `--refer-video`, `--voice-id`, `--tag`, `--sound-file`, `--voice-speed`, `--pack`) and says `--help` is the authority; the deliberate all-or-nothing status policy is stated (one unrecognised status word fails the whole envelope rather than guessing about a paid task); `{ path }` carries an explicit "never build this from untrusted input" caution; `extraSettings`/`extraOptions` carry their trust assumption; and the price table now says plainly that **what a failed task costs is neither vendor-documented nor measured here**. `@example` blocks on `textToVideo`, `save`, `tasks.recover` and `parseCallback` (typechecked against the built types).
- Two upstream documents that contradicted the code are corrected rather than silently edited: the spec's retry table claimed downloads retry (they never did — the row now says NOT IMPLEMENTED and records the intent), and the checklist's Q11 said flatly "It IS an idempotency key" where the evidence is a single `text-to-video` probe after a *successful* create — the scope the double-bill guidance rests on is a Phase 7 probe, not a closed question.
- `noUncheckedIndexedAccess` is on. Every array/record index in `src/` is now `T | undefined` at the type level, which turned the ~10 ad-hoc `params.x![i]` re-reads in `products/{video,image,resources}` into one shared `redactList()` helper (a resolved list is redacted against the array it was derived from, once, and a missing source drops the entry instead of asserting); made the IPv4 half of the SSRF guard fail closed on a malformed quad rather than rest on its callers gating with `net.isIP`; and replaced the "the regex is total, this check is for the reader" comment in the CLI with real fallbacks. No runtime behaviour changed except those two guards.
- Public surface completed before 2.0.0 ships (these would be breaking after publish): `TtsParams` and `HttpCoreInternals` are exported from the root — `client.audio.tts()` was the only create method whose params type a consumer could not name, and `HttpCoreInternals` types the second parameter of the public `KlingClient` constructor. `LedgerPage<T>` and `PollOptions<T>` are constrained (`T extends DeductionEntry` / `T extends Task`).
- `tasks.get()` rethrows the caller's own abort unwrapped instead of wrapping it in `KlingBatchError` ("chunk 1 of 1 failed"), matching `HttpCore` and `download`. A consumer matching on `signal.reason` no longer has to unwrap a batch error to recognise their own cancel; `client.healthCheck()` likewise rethrows a caller abort rather than reporting `false`, so a cancelled probe is not a verdict of "API down".
- CLI: `int()`/`num()` reject an empty or whitespace-only value instead of reading it as `0` (a shell variable that expanded to nothing submitted `0`); `reportError` survives a non-object throw (`null`, a string) rather than failing inside the error reporter; a failed read of the package manifest names itself on stderr instead of silently reporting `--version 0.0.0`.
- `KlingAPIError.externalId` is set (mirroring `request.externalId`) like every other request-bearing error — the README's recovery guidance said `err.externalId` was set after a `may-exist`, which was untrue for the one error class a `5000`/`5002` actually produces.
- README: the recovery protocol now says the one thing that closes the double-bill corridor — re-submit after `may-exist` **with the same `externalTaskId`** (`err.externalId`), never a fresh UUID, with a typed example; `wait()`'s outcome list names `KlingTaskNotFoundError` and states that a `KlingPollTimeoutError` leaves the task running and billed; "downloads are not retried" is stated (the spec's D10 row said they were — the code never did); `DEFAULT_POLL_TIMEOUT`'s rationale no longer cites 1.x "pro mode".
- `wait()` / `poll()` validate their timing options: `intervalMs` must be a finite number > 0 and `deadlineMs` > 0 and either `Infinity` or ≤ 2 147 483 647 ms, else `KlingValidationError` — before the first request. Before this, `intervalMs: NaN` (an unset `Number(process.env.X)`) or `0` polled `GET /tasks` at ~800 req/s until the vendor's 429 backoff bit, and a deadline past ~24.8 days overflowed `setTimeout` and fired `KlingPollTimeoutError` in milliseconds with `task: null`.
#### Fixed before release

- `KlingSaveError.leftover?: { path, cause }` names the failed write's temp file (`<file>.<pid>.part`) when its removal fails too (EACCES on the directory, EBUSY on Windows); the message says so. Before this the cleanup error was swallowed and the orphan was named by neither `written` nor the error, so a consumer cleaning up from `written` left it behind.
- `retry` options are resolved field by field and validated: `retry: { maxAttempts: undefined }` kept the default before only by luck of the spread — with an explicitly undefined key it disabled the attempt cap (a permanent 5xx retried forever); `client.save()` no longer pins the download deadline to the API `timeout` (the 120 s video default was unreachable from the client and CLI); an fs error while writing is a `KlingSaveError` too, with the partial file removed; the retry backoff timer is cleared on abort and its listener released on completion.

#### What 2.0.0 is

A full reboot against the current Kling API (spec: `docs/specs/kling-api-2.0-migration-spec-v0_4_3.md`;
build record: `docs/specs/kling-api-2.0-migration-checklist.md`). The vendor discontinued every model
1.x defaulted to, moved video generation to a path-per-model API standard, and made a static API Key
the only credential that works there; 1.x cannot generate video against the current API. Nothing
from 1.x is source-compatible — see the README's migration table.

**Semantics that changed without a type-signature change** (the compiler will not catch these):
the `TaskStatus` terminal value is `succeeded` (the legacy `succeed` is normalized); every default
model changed and the policy behind them is "cheapest current-generation with native audio" for video,
"newest" for image; a bare string media argument is a URL or Base64 and is **never** a filesystem
path (`{ path }` for files); `outputsExpireAt` is derived on every succeeded task and `save()` refuses
an expired one; the unified `GET /tasks` is chunked at 20 ids.

### Added
- Kling 3.0 / 3.0 Turbo / 3.0 Omni / O1 / 2.6 / 2.5 Turbo video via the new API standard; motion control; elements and voices; TTS; normalized `Task`/`TaskHandle`; webhook signature verification.
- `kling` CLI rebuilt on the 2.0 tree: `video t2v|i2v|omni|motion-control`, `image generate|omni|multi|outpaint|subject-completion`, `elements`/`voices` `create|get|list|presets|delete`, `avatar create`, `audio tts`, `tasks get|list|get-by-product|list-by-product|recover`, `account usage|balance|packages`; globals `--api-key --output-dir --json --debug -q`; credential chain `--api-key` → `KLING_API_KEY` → `./.env` → `~/.kling/.env` (the CLI, not the library, reads `.env` files); `--wait` polls behind a spinner and saves unless `--no-download`; errors exit 1 with the cause chain. Removed: `--access-key`, `--secret-key`, `--mode` (except `avatar`), `--cfg-scale`, `--negative-prompt` on video, `--camera-*`, `--image-tail` (→ `--last-frame`).
- `client.account.{usage, balanceLedger, packageLedger}` (resource packages with remaining units; per-task cash / unit deduction ledgers, cursor-paged, camelCase) and `parseCallback(rawBody, { headers, secret })` / `verifyWebhookSignature()` implementing the vendor's Standard-Webhooks scheme — the published test vector passes; with a secret, a missing header set, bad signature or > 5 min skew throws `KlingWebhookError` and no task is returned; without a secret `verified: null` marks the body **unauthenticated**. `rawBody` must be the exact bytes received.
- `client.elements.{create, get, list, presets, delete(id, { kind })}`, `client.voices.{create, get, list, presets, delete}`, `client.avatar.create()`, `client.audio.tts()` (synchronous — returns `audio` outputs; no external id, a lost response is unrecoverable). Live-verified 2026-09-20 through the library: TTS 0.05 units, voice create from the clip 0.05 units, element create 0 units; **an element deletes through either documented path** (created via `advanced-custom-elements`, deleted via `delete-elements` → status `deleted`; the second delete answers `1201` "already be deleted"), so the two paths share one library. The delete endpoints may answer `code 0` with no `data`; the library treats that as success.
- `client.image.{generate, omni, multiImageToImage, outpaint, subjectCompletion}` on the legacy `/v1/` standard with the API Key — defaults `kling-v3` / `kling-v3-omni` (newest, D7), `multiImageToImage` fixed to `kling-v2-1`; `IMAGE_MODELS` registry (`imageReference`/`humanFidelity` are `kling-v2-1`-only errors; O1 has no 4k and no series); `outpaint` replaces 1.x `expandImage`; `subjectCompletion` is new. Live-verified 2026-09-20: `image.generate` n=1 1k → 8 image units, `tasks.recover` by external id found it, and on that one task the vendor's signed URL `Expires=` matched the library's derived 30-day `outputsExpireAt` within 2 s (n=1, legacy image; video URLs not yet compared).
- `client.save(task, dir, opts)` / `save()` — downloads every output through the client's `fetch` with a byte cap (default 500 MiB), a redirect cap (5) and a per-hop SSRF check; `KlingOutputsExpiredError` before any fetch once the derived 30-day expiry has passed (`force` bypasses); files `<task.id>-<index>.<ext>` plus a `<task.id>.json` sidecar carrying the redacted request. `MediaSource` now also takes `{ path }`, `Buffer` and `Uint8Array` (extension, magic bytes, ≥ 300 px, 1:2.5–2.5:1 aspect, then Base64). The URL safety check resolves hostnames and refuses any that map to a private, loopback, link-local, multicast or metadata address — in IPv4 (all spellings) and IPv6 (`::1`, `fc00::/7`, `fe80::/10`, mapped v4); a DNS failure fails closed. **Time-of-check only:** the resolved address is not pinned into the connection.
- `client.video.omni()` (default `kling-3.0-omni`; `kling-o1`) and `client.video.motionControl()` (default `kling-3.0`; `kling-2.6`) — seven omni content types with auto ids (`image_n`, `video_1`, `element_n`), the vendor's element/reference-image count matrices (exact cells when `elements[].kind` is given, kind-independent envelopes otherwise), `baseVideo`/`featureVideo` audio and multi-shot constraints as `[shape]` rules, O1's multi-image-only / 5|10 s rules; motion control's `characterOrientation`, URL-only motion video, element on 3.0 only. Live-verified 2026-09-20: omni first-frame-only 3 s / 720p / silent → 1.8 units (= the silent rate).
- `client.video.imageToVideo()` → `POST /image-to-video/<model>` with `contents[]` (prompt, first_frame, last_frame, element*, voice*, `extraContents`); `firstFrame`/`lastFrame` are `MediaSource`s — an https URL, a Base64 string (optional `data:` prefix), `{ url }` or `{ base64 }` on this build; `{ path }`/`Buffer` arrive with Phase 2c. **A bare string is never read as a filesystem path.** Inline caps 20 MB (new standard) / 10 MB (legacy), 40 MB encoded per request; a create's deadline grows 4 s per MB of body. `@name` prompt references with no matching content `id` log a warning.
- `client.video.textToVideo()` → `POST /text-to-video/<model>` on the new standard, default `kling-3.0-turbo`; `VIDEO_MODELS` capability registry for the six current video ids with `[shape]`/`[capability]` validation, `unknownModels: 'passthrough' | 'reject'`, `capabilityValidation: 'error' | 'warn'`, and `extraSettings`/`extraOptions` escape hatches (a modeled key in either is rejected). Live-verified 2026-09-20: a 3 s / 720p create cost 2.4 video units and the mp4 carries an AAC audio track with no `audio` field sent — native audio is always on for 3.0-turbo; the vendor **rejected a duplicate `external_task_id`** (`1201` "already exists") on the one case tried — an immediate t2v re-submit after a success — so it behaves as an idempotency key there; legacy creates, other products and re-submits after a failure or after time have not been observed.
- `client.tasks` — `get(ids, { byExternalId })` (unified `GET /tasks`, chunked at **20** ids per request: the live API rejects 21 with `1201`, a cap the vendor docs do not state), `list()` (`POST /tasks` cursor), `getByProduct`, `listByProduct`, `recover(product, externalId)`, `handle()`; `TaskHandle.wait()` shares one poll loop across concurrent callers with per-caller deadline and abort; `client.healthCheck()`; `KlingTaskNotFoundError` (a lookup the vendor answers with `data: []` or a not-found `1201`).
- Codec parse policy: an unknown top-level task status or a wrong-standard envelope throws `KlingCodecError` (never reads as `processing`); a malformed *output* entry is dropped with a logger warning, never a throw; timestamps below 1e11 are read as seconds and scaled with a warning; `Task.outputsExpireAt = updatedAt + 30 d` is derived on `succeeded` tasks from the vendor's stated retention.

### Changed
- `TaskStatus` value `succeed` → `succeeded` (same type, different value — a semantics-without-signature change); every default model; a bare-string media argument is a URL or Base64, never a filesystem path.
- `engines.node` `>=18` → `>=20` (native `fetch`; CI matrix is 20 and 22). Package entry points `dist/api.js` → `dist/index.js`; `bin.kling` → `dist/cli/index.js`.

### Removed
- AccessKey/SecretKey JWT authentication; `extendVideo`; `multiImageToVideo`; the `./api`, `./auth`, `./utils`, `./config`, `./types` subpath exports (only `.` and `./package.json` remain); the `axios` and `jsonwebtoken` runtime dependencies; semantic-release automation.

- Comprehensive TypeScript type definitions (118+ exported types)
- 534 tests with 95.29% statement coverage
- Production security features:
  - API key redaction in logs
  - SSRF protection with IPv4-mapped IPv6 bypass prevention
  - HTTPS enforcement
  - Error sanitization in production mode
  - Parameter validation before API calls
- Auto-polling with animated spinner UI
- Retry logic with exponential backoff (2s, 4s, 8s)
- Organized data storage with timestamped files and metadata JSON
- Submodule exports for tree-shaking optimization
